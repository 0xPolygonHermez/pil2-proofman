Recursion setup · linear-hash model

Cell & GPU-memory decision map

Each cell is a recursive-verifier configuration at dimension 2N and blowup 2b, folding factor 3, Merkle arity set by the hash (blake3 binary, blake2b quaternary). Hash counts mirror setup/pil2-stark/src/verifier_hashes.rs rule for rule — leaf (linear) hashes, Merkle authentication paths to lastLevelVerification, per-tree root reductions, and the real generate_stark_struct FRI schedule. Only the Fiat-Shamir transcript and the grinding check are left out; grinding costs the verifier one hash, since it checks a nonce and the 2bits is all prover work. Paths dominate, typically 60–75% of the total. Color is estimated prover GPU memory; a teal ring marks feasible configs: the verifier self-fits, a ZisK Main proof fits the recursion cell budget, and prover memory stays under 32 GB.

Blake3's stage widths are measured on the test-recursive recursion air rather than extrapolated from the examples/hashes precompile — see the table below. stage1 = 59k + 20: a lane costs 59 columns and the 18-wide plonk band plus 2 multiplicity columns are shared, so the width is affine in k, not proportional. fixed = 42. Widths also move along the blowup axis: a blowup of 2b lets the quotient span 2b chunks, so the PIL can be compiled at maxDeg = 2b + 1 — 3 at 21, 5 at 22, 8 from 23 on — and a higher degree lets std_sum pack more bus terms behind each im. The blowup 2 row is measured at k = 2, 3, 4 and 5 (stage1 138/197/256/315, stage2 69/93/117/141), so the k-dependence is fitted rather than assumed; the other blowups are the model's own im arithmetic. Self-fit is still a fixed point — each added lane widens the trace the verifier must itself hash — and note the direction that matters for the layer above: LANES trades rows for columns, and the next recursion layer pays for the columns, so packing more lanes shortens this air and makes the one verifying it more expensive. Switch the hash to compare Blake3 (56 clocks) against Blake2b (96 clocks); blake2b's lane geometry remains extrapolated. The low-degree test switches between FRI and STIR — see the STIR card below the grid for what changes and what deliberately does not.

Two columns a lane, and nEvals goes down by the eight columns' own openings rather than up. va cannot follow: blake3Add3Check is cubic in the sum, so a degree-2 operand lands at 7 against maxDeg 5.

Two things this table settles. Plonk is not where blake3 pays: 135,942 constraints against poseidon2's 268,969, on a fixture where blake3's air is nonetheless 4.8× the columns — what blake3 costs is the 8,661 blocks of 56 rows, and the band rides free inside their interiors (84,404 rows placed in 1,761 of them, 415,728 available). The 67 opening points are the clock selectors: air.CLK[i] = (i)'CLK_0 reads primes at depth 0..55, and every distinct offset is an opening point — which is what makes the layer above a blake3 recursion expensive, since recursive2's work scales with the width and opening count beneath it.

The LANES sweep, same fixture, --blake3-lanes k. Why the air ships at 4: the block count is ceil(34,638 / k) and 4 is the largest k whose blocks still fit 2^19 — 3 needs 11,548 of them, 646,688 rows, and the air doubles. The layer above wants the opposite, since it hashes this air's leaves: 197 columns at k=3 against 256 at k=4. Both columns of the trade are here, and neither is free.

FRI vs STIR — what the selector changes

STIR (Arnon–Chiesa–Fenzi–Yogev, ePrint 2024/390) landed in the repo as security::pcs::Stir, a soundness calculator with the same Pcs interface as Fri. It is not wired into generate_stark_struct or the prover, so the STIR column is what the recursion cell would cost, not what the pipeline does today. The solver here is a port of that file — validated against every #[test] in it, query vectors and all — so the page and the Rust agree by construction.

The mechanism, which is the part that reads as a bug until you see it. FRI folds the domain by 2k each layer, so the rate never moves and every layer costs the same q openings. STIR only halves the domain while dropping the degree by 2k — mi+1 = mi − k, μi+1 = μi + (k − 1), so the domain loses exactly one bit whatever k is — and the rate improves every round. A better rate needs fewer queries, so ti collapses. Taller trees, far fewer openings:

Held equal on purpose, so the delta is the low-degree test and nothing else. The trace commitment is modelled the same for both — four trees at the full extended domain, one row per leaf — opened t0 times. Under STIR f0 is really coset-committed, which would make its tree 2k shallower and its paths shorter, so the STIR column is if anything pessimistic. The folding schedule is the family's own measured FRI factor, stopped at the same final degree; stir.rs's tests use hand-tuned schedules that run a round deeper. Batch size moves only STIR's batching grinding, never the query schedule (checked from 2 to 105), so it cannot flatter either column.

Where the win lands. The recursion cell is hash-bound, so 23% fewer verifier hashes is 23% fewer BLAKE3 compressions in the layer above — and since blocks are what size the air (8,661 of them, 56 rows each, in the measured column), it is the one lever that moves the arity-2 wall without touching the AIR. Prover memory does not move, because STIR's oracles stay tall exactly as much as they shed queries.

At powBits 24 and blowup 2 the closed form gives 106 queries, which is what the pipeline generated · Merkle arity per hash family (see below) · digest 4 field elements · target 128-bit (JBR) · extension degree 3 · leaf hashes are block compressions, not rate-limited sponge absorptions: blake3 takes 8 elements per 64-byte block plus a parent per extra 1024-byte chunk, blake2b 16 per 128-byte block · Merkle paths stop at the lastLevelVerification the slider sets (generate_stark_struct defaults it to floor(log_arity(16)) — a 16-node bottom level at every arity, so 4 levels at arity 2 and 2 at arity 4) and each tree pays its root reduction once, as merkleTreeGL does — llv counts LEVELS at any arity, so the kept level holds arity^llv nodes: 16 at arity 4, 4 at arity 2 · FRI or STIR, selectable · FRI query counts from security::pcs::Fri (JBR, closed form) and STIR's from a port of security::pcs::Stir validated against every test in stir.rs — the same calculators that size proving keys · the folding factor is read off each family's measured starkStruct (blake3 4, poseidon2 3) · blake3 = 56 clocks × the lane width at the chosen blowup; stage1 = 59k+20, fixed 42, stage2 and stageQ follow maxDeg = min(2^b+1, 8) — measured at k = 2, 3, 4 and 5 / blowup 2 on the test-recursive recursion air (42 / 256 / 117 / 12 at k=4), the rest of the grid extrapolated by the model's im arithmetic; blake2b = 96 clocks, stage1 98k+2, fixed 6, full 12-round — blake2b.pil pins NUM_ROUNDS = 12 and has no LANES parameter, so its per-lane split is extrapolated from the same bus decomposition (52 lane-local lookups + 2 shared) · Merkle arity follows the compression block: blake3 folds 2 digests per 64B block (binary tree), blake2b folds 4 per 128B block (quaternary) — one permutation per node either way · Main: nBits 22, blowup 1, fixed 3 / stageQ 6 / stage2 24 / stage1 38, 3 opening points, 61 functions, not blake-packed.
