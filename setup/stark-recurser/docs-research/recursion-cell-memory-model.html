Recursion setup · linear-hash model

Cell & GPU-memory decision map

Each cell is a recursive-verifier configuration at dimension 2N and blowup 2b, folding factor 3, Merkle arity set by the hash (blake3 binary, blake2b quaternary). Hash counts mirror setup/pil2-stark/src/verifier_hashes.rs rule for rule — leaf (linear) hashes, Merkle authentication paths to lastLevelVerification, per-tree root reductions, and the real generate_stark_struct FRI schedule — and reproduce that crate's counts exactly on all three airs of the hashes example (the Rust was in turn checked against an instrumented native verifier). Only the Fiat-Shamir transcript and the grinding check are left out, together about 1.5%. Paths dominate, typically 70–75% of the total. Color is estimated prover GPU memory; a teal ring marks feasible configs: the verifier self-fits, a ZisK Main proof fits the recursion cell budget, and prover memory stays under 32 GB. Stage widths come from packing k blake3 lanes side by side and are affine in k, not proportional: stage1 = 53k + 2. They also move along the blowup axis: a blowup of 2b lets the quotient span 2b chunks, so the PIL can be compiled at maxDeg = 2b + 1 — 3 at 21, 5 at 22, 8 from 23 on (Compressor.pil's own ceiling) — and a higher degree lets std_sum pack more bus terms behind each im. Measured over LANES 1–4 × blowup 1–3: a lane costs 53 + 42 columns at 21, 53 + 21 at 22, 53 + 12 at 23, with stageQ going 6 → 12 → 21 and fixed = 8 throughout. Self-fit is still a fixed point (each added lane widens the trace the verifier must itself hash) but the shared columns are paid once. Switch the hash to compare Blake3 (56 clocks) against Blake2b (96 clocks) — each carries its own lane geometry. Low-degree test is FRI.

Model ported from pil2-stark types::cells + pil::info::get_prover_memory · grinding configurable (slider, default 20) · Merkle arity per hash family (see below) · digest 4 field elements · target 128-bit (JBR) · extension degree 3 · leaf hashes are block compressions, not rate-limited sponge absorptions: blake3 takes 8 elements per 64-byte block plus a parent per extra 1024-byte chunk, blake2b 16 per 128-byte block · Merkle paths stop at the lastLevelVerification the slider sets (generate_stark_struct defaults it to floor(log_arity(16)) — a 16-node bottom level at every arity, so 4 levels at arity 2 and 2 at arity 4) and each tree pays its root reduction once, as merkleTreeGL does — llv counts LEVELS at any arity, so the kept level holds arity^llv nodes: 16 at arity 4, 4 at arity 2 · FRI only · query counts from security::pcs::Fri (JBR, closed form), the same calculator that sizes proving keys · blake3 = 56 clocks × the lane width at the chosen blowup — marginal lane 95 cols at 2^1, 74 at 2^2, 65 at 2^3, while the panel reports the amortized width (stage1+stage2)/k, which also carries the shared columns: 97 / 76 / 67 at k=4, 103 / 79 / 70 at k=1; stage1 = 53k+2 always, stage2 and stageQ follow maxDeg = min(2^b+1, 8) — all twelve LANES 1-4 × blowup 1-3 points measured with proofman-setup stats; blake2b = 96 clocks, stage1 98k+2, fixed 6, full 12-round — blake2b.pil currently pins NUM_ROUNDS = 8 and has no LANES parameter, so its per-lane split is extrapolated from the same bus decomposition (52 lane-local lookups + 2 shared) · Merkle arity follows the compression block: blake3 folds 2 digests per 64B block (binary tree), blake2b folds 4 per 128B block (quaternary) — one permutation per node either way · Main: nBits 22, blowup 1, fixed 3 / stageQ 6 / stage2 24 / stage1 38, 3 opening points, 61 functions, not blake-packed.
