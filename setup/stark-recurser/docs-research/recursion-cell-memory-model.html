Recursion setup · linear-hash model

Cell & GPU-memory decision map

Each cell is a recursive-verifier configuration at 2N rows, blowup 2b, folding factor 3, Merkle arity from the hash (blake3 and SHA-256 binary, blake2b quaternary). Hash counts mirror verifier_hashes.rs rule for rule — leaf hashes, Merkle paths to lastLevelVerification, per-tree root reductions, the real generate_stark_struct schedule. Transcript and grinding are left out. Paths dominate, 60–75% of the total. Color is prover GPU memory; a teal ring marks feasible: the verifier self-fits, a ZisK Main proof fits the cell budget, and memory stays under 32 GB.

Blake3's stage widths are measured on the test-recursive recursion air, not extrapolated from the examples/hashes precompile. stage1 = 59k + 20, affine in k rather than proportional: a lane costs 59 columns, the 18-wide plonk band and 2 multiplicity columns are shared. fixed = 42. Widths also move along the blowup axis — 2b lets the quotient span 2b chunks, so maxDeg = min(2b+1, 8) and a higher degree lets std_sum pack more bus terms behind each im. Blowup 2 is measured at k = 2/3/4/5 (stage1 138/197/256/315, stage2 69/93/117/141); other blowups are the model's own im arithmetic. Self-fit is a fixed point — each lane widens the trace the verifier must hash itself — and LANES trades rows for columns while the next layer pays for the columns, so packing lanes shortens this air and makes the one verifying it dearer. Blake3 is 56 clocks, SHA-256 72, Blake2b 96 — and only blake3's lane geometry is a recursion air. SHA-256's is the examples/hashes precompile, anchored to its one measured point (115 committed columns × 72 clocks = 8,280 cells at LANES 1, blowup 1). Its lane does not amortize with k — sha2.pil has no LANES parameter to share columns across — but it does move along the blowup axis, and the wrong way: 8,280 → 8,496 → 9,144 at blowup 1/2/3. Degree headroom lets std_sum cluster more bus terms behind each im, but the im constraint then becomes the air's highest-degree one, so stageQ grows unconditionally. Blake3 wins that trade with 48 columns of stage2 to give back; sha2 has 6, so it pays the stageQ growth for almost nothing. Blake2b's is extrapolated. Read SHA-256's cells as a floor, not a like-for-like — blake3's own precompile is 4,382 against the 5,264 its recursion air costs at the same k=4/blowup 2, a 20% gap, and 115 counts stageQ where blake3's 94 does not.

Hash rules follow pil2-stark verifier_hashes.rs — pinned against an instrumented native verifier for FRI, a structural mirror of STIR::verify for STIR; memory follows pil::info::get_prover_memory.
· digest 4 field elements · extension degree 3 · target 128-bit (JBR) · Merkle arity per hash family · grinding on the slider, starting at hash_family::recursive_grinding_bits (24 blake3, 20 poseidon, blake2b extrapolated to 24).
· Leaf hashes are block compressions, not rate-limited sponge absorptions: blake3 8 elements per 64-byte block plus a parent per extra 1024-byte chunk, blake2b 16 per 128-byte block, SHA-256 ceil((8w+9)/64) because FIPS appends the terminator and length as message data (one extra block exactly when w mod 8 is 0 or 7). Merkle arity follows the block — blake3 and SHA-256 fold 2 digests per 64B block (binary), blake2b 4 per 128B (quaternary) — one permutation per node, which for SHA-256 holds only under a domain-separated, length-free node hash; with literal FIPS nodes a 64-byte arity-2 node costs two compressions and that variant is not modelled here.
· Paths stop at the slider's lastLevelVerification, which counts LEVELS at any arity, so the kept level holds arity^llv nodes; each tree pays its root reduction once, as merkleTreeGL does. generate_stark_struct defaults it to floor(log_arity(16)).
· Query counts come from security::pcs::Fri and a port of security::pcs::Stir — the same calculators that size proving keys. At powBits 24 / blowup 2 the closed form gives 106, which is what the pipeline generated. Folding factor is read off each family's measured starkStruct (blake3 4, poseidon2 3).
· SHA-256 = 72 clocks (sha2.pil: 4 load-state + 16 load-input + 48 mixing + 4 write-state), fold 4 and grinding 24 read off a real sha256 proving key, block/arity/padding exact arithmetic. Its WIDTHS are anchored to the examples/hashes precompile at LANES 1 / blowup 1 — fixed 5, stage1 103, stage2 6, stageQ 6, 115 committed — with bus 3 back-fitted from that stage2 so the model reproduces the point and runs its own im arithmetic above it. stage1 does not amortize with k (no LANES parameter to share across) and no sha256 recursion air exists to fit a slope to; building one is what would pin it. Its laneCols counts stageQ, following README.md's cells/hash convention, where the recursion-air families' does not. Earlier revisions instead scaled blake3's recursion slopes by the two precompiles' widths (103/53); measured, sha2's stage2 is 6 against blake3's 48, so that overstated its bus by roughly 8x and its cells/permutation by 50%.
· blake3 = 56 clocks × the lane width; stage1 59k+20, fixed 42, stage2/stageQ follow maxDeg — measured at k = 2/3/4/5, blowup 2, on the test-recursive air (42/256/117/12 at k=4), the rest extrapolated. blake2b = 96 clocks, stage1 98k+2, fixed 6, 12 rounds; blake2b.pil has no LANES parameter, so its per-lane split is extrapolated from the same bus decomposition (52 lane-local lookups + 2 shared).
· Main: nBits 22, blowup 1, fixed 3 / stageQ 6 / stage2 24 / stage1 38, 3 opening points, not blake-packed.
